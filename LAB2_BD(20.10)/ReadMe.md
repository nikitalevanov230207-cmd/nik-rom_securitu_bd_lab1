# Лабораторная работа №2 по разработке и защите базы данных в MS SQL Server

## Общие положения

Любая задача по обеспечению надёжности и отслеживаемости базы данных начинается с анализа предметной области, выделения критически важных операций и обоснования выбора стратегии аудита и резервного копирования. Указанные в задании механизмы должны быть реализованы в виде набора SQL-скриптов, обеспечивающих как автоматическое журналирование событий, так и возможность восстановления данных при различных сценариях сбоев.

Особое внимание следует уделить корректному выбору типа резервной копии (полная, разностная, журнала транзакций, копии файловой группы, копии для копирования, копии хвоста журнала) в зависимости от характера моделируемого инцидента.

## Методические рекомендации по выполнению лабораторной работы

### 1. Подготовка базы данных к аудиту и резервному копированию

Перед началом работы убедитесь, что база данных переведена в **полную модель восстановления** (`FULL`). Это необходимое условие для создания резервных копий журнала транзакций и выполнения точечного восстановления. В простой (`SIMPLE`) модели восстановления журнал транзакций автоматически усечён после каждого контрольного точки, что делает невозможным восстановление на конкретный момент времени.

Проверьте текущую модель восстановления и при необходимости измените её:

```sql
SELECT name, recovery_model_desc
FROM sys.databases
WHERE name = 'MyDB';

ALTER DATABASE MyDB SET RECOVERY FULL;
```

> **Примечание.** После смены модели восстановления на `FULL` необходимо создать полную резервную копию, чтобы цепочка журнала транзакций начала формироваться.

Также убедитесь, что в базе данных создана отдельная файловая группа для хранения данных аудита. Размещение таблицы аудита в изолированной файловой группе позволяет отделить журнал действий от основных данных, что упрощает управление пространством и повышает отказоустойчивость.

```sql
ALTER DATABASE MyDB
ADD FILEGROUP FG_Audit;

ALTER DATABASE MyDB
ADD FILE (
    NAME = 'MyDB_Audit',
    FILENAME = 'C:\SQLData\MyDB_Audit.ndf',
    SIZE = 3MB,
    MAXSIZE = 20MB,
    FILEGROWTH = 2MB
) TO FILEGROUP FG_Audit;
```

### 2. Создание таблицы аудита

Таблица аудита должна содержать информацию, достаточную для однозначной идентификации события: кто выполнил действие, над какой таблицей, какого типа было действие, какие данные были до и после изменения, и когда это произошло.

Рекомендуемый минимальный набор столбцов:
- идентификатор записи аудита (первичный ключ, `IDENTITY`);
- имя таблицы, в которой произошло изменение;
- тип операции (`INSERT`, `UPDATE`, `DELETE`);
- первичный ключ изменённой записи;
- старое и новое значения (в текстовом представлении);
- имя пользователя (`SYSTEM_USER` или `SUSER_SNAME()`);
- дата и время события (`GETDATE()`).

```sql
CREATE TABLE dbo.Audit (
    AuditID INT IDENTITY(1,1) PRIMARY KEY,
    TableName NVARCHAR(128) NOT NULL,
    OperationType CHAR(6) NOT NULL,     -- INSERT / UPDATE / DELETE
    RecordID INT NOT NULL,              -- PK of changed record
    OldValue NVARCHAR(MAX) NULL,
    NewValue NVARCHAR(MAX) NULL,
    UserName NVARCHAR(128) NOT NULL,
    EventTime DATETIME2 NOT NULL DEFAULT GETDATE()
) ON FG_Audit;                          
```

### 3. Ограничение доступа к таблице аудита

Таблица аудита содержит критически важную информацию о действиях пользователей и не должна быть доступна для модификации никому, включая администратора базы данных. Администратору предоставляется **только** право чтения. Все остальные роли должны быть явно лишены любого доступа.

Используйте `DENY` для запрета доступа всем ролям и `GRANT SELECT` только для роли администратора:

```sql
DENY SELECT, INSERT, UPDATE, DELETE ON dbo.Audit TO Librarian;
DENY SELECT, INSERT, UPDATE, DELETE ON dbo.Audit TO Reader;
DENY SELECT, INSERT, UPDATE, DELETE ON dbo.Audit TO InventoryManager;

GRANT SELECT ON dbo.Audit TO Admin;
```

> **Примечание.** Триггеры записывают данные в таблицу `Audit` в контексте пользователя, вызвавшего изменение. Поскольку `DENY` блокирует и запись через триггер, необходимо использовать механизм подписи модулей или разрешить `INSERT` для триггеров отдельно. На практике в учебных целях допускается предоставление `INSERT` на таблицу аудита ролям, но `DENY` на `SELECT`, `UPDATE`, `DELETE`.

### 4. Создание триггеров для журналирования

Триггеры типа `AFTER` срабатывают после успешного выполнения DML-операции и позволяют зафиксировать факт изменения данных. Внутри триггера доступны псевдотаблицы `inserted` (новые значения) и `deleted` (старые значения):
- при `INSERT`: `inserted` содержит новые строки, `deleted` пуста;
- при `DELETE`: `deleted` содержит удалённые строки, `inserted` пуста;
- при `UPDATE`: `inserted` содержит новые значения, `deleted` — старые.

```sql
CREATE TRIGGER trg_Books_Audit
ON dbo.Books
AFTER INSERT, UPDATE, DELETE
AS
BEGIN
    SET NOCOUNT ON;

    -- INSERT logged
    INSERT INTO dbo.Audit (TableName, OperationType, RecordID, NewValue, UserName)
    SELECT 'Books', 'INSERT', BookID, CAST(Title AS NVARCHAR(MAX)), SYSTEM_USER
    FROM inserted
    WHERE NOT EXISTS (SELECT 1 FROM deleted WHERE deleted.BookID = inserted.BookID);

    -- DELETE logged
    INSERT INTO dbo.Audit (TableName, OperationType, RecordID, OldValue, UserName)
    SELECT 'Books', 'DELETE', BookID, CAST(Title AS NVARCHAR(MAX)), SYSTEM_USER
    FROM deleted
    WHERE NOT EXISTS (SELECT 1 FROM inserted WHERE inserted.BookID = deleted.BookID);

    -- UPDATE logged
    INSERT INTO dbo.Audit (TableName, OperationType, RecordID, OldValue, NewValue, UserName)
    SELECT 'Books', 'UPDATE', i.BookID,
           CAST(d.Title AS NVARCHAR(MAX)),
           CAST(i.Title AS NVARCHAR(MAX)),
           SYSTEM_USER
    FROM inserted i
    JOIN deleted d ON i.BookID = d.BookID;
END;
```

> **Примечание.** В задании не требуются массовые операции в триггере, однако триггер должен корректно обрабатывать множественные строки (используйте `JOIN` между `inserted` и `deleted`, а не скалярные переменные).

### 7. Резервное копирование: полная и разностные копии в отдельные файлы

Резервное копирование в SQL Server реализуется командой `BACKUP DATABASE`. **Полная копия** (`FULL`) содержит все данные базы на момент создания. **Разностная копия** (`DIFFERENTIAL`) содержит только те экстенты данных, которые изменились с момента последней полной копии. Разностные копии создаются быстрее и занимают меньше места, но для восстановления всегда требуется базовая полная копия.

Каждая разностная копия в данном примере сохраняется в **отдельный файл** (используется `WITH INIT`, который перезаписывает содержимое файла и указывается новое имя файла):

```sql
BACKUP DATABASE MyDB
TO DISK = 'C:\Backups\MyDB_Full.bak'
WITH INIT, NAME = 'Full Backup';

-- ... something happens with data in DB ...

BACKUP DATABASE MyDB
TO DISK = 'C:\Backups\MyDB_Diff1.bak'
WITH DIFFERENTIAL, INIT, NAME = 'Differential 1';

-- ... something happens with data in DB ...

BACKUP DATABASE MyDB
TO DISK = 'C:\Backups\MyDB_Diff2.bak'
WITH DIFFERENTIAL, INIT, NAME = 'Differential 2';
```

> **Примечание.** При внесении изменений (пункты 6 и 9 задания) соблюдайте указанное соотношение вставок, обновлений и удалений. Для генерации тестовых данных допустимо использовать цикл `WHILE` или конструкцию `INSERT INTO ... SELECT`.

### 8. Перевод базы данных в автономный режим и удаление файлов

Для имитации аппаратного сбоя необходимо перевести базу данных в автономный режим и удалить один или несколько физических файлов. Перевод в `OFFLINE` освобождает файлы от блокировки процессом SQL Server, после чего их можно удалить средствами ОС или через `xp_cmdshell`.

```sql
ALTER DATABASE MyDB SET OFFLINE WITH ROLLBACK IMMEDIATE;

EXEC sp_configure 'show advanced options', 1; RECONFIGURE;
EXEC sp_configure 'xp_cmdshell', 1; RECONFIGURE;

EXEC xp_cmdshell 'del "C:\SQLData\MyDB.mdf"';
EXEC xp_cmdshell 'del "C:\SQLData\MyDB.ldf"';

EXEC sp_configure 'xp_cmdshell', 0; RECONFIGURE;
EXEC sp_configure 'show advanced options', 0; RECONFIGURE;
```

> **Важно.** Перед удалением файлов убедитесь, что у вас есть актуальные резервные копии. Удаление файла `.ldf` без предварительной резервной копии журнала транзакций может привести к безвозвратной потере данных.

### 9. Восстановление из полной резервной копии

Восстановление выполняется командой `RESTORE DATABASE`. Параметр `WITH REPLACE` позволяет перезаписать существующую базу данных. Если после восстановления планируется накатывать разностные копии или журналы транзакций, используйте `WITH NORECOVERY` — это оставит базу в состоянии восстановления.

```sql
RESTORE DATABASE MyDB
FROM DISK = 'C:\Backups\MyDB_Full.bak'
WITH REPLACE, NORECOVERY;

RESTORE DATABASE MyDB
FROM DISK = 'C:\Backups\MyDB_Diff2.bak'
WITH RECOVERY;    -- RECOVERY finalize restore proccess
```

> **Примечание.** При восстановлении файловых групп используйте конструкцию `RESTORE DATABASE ... FILEGROUP = 'FG_Name'`. Это позволяет восстановить отдельную файловую группу, не затрагивая остальные данные.

### 10. Резервное копирование: разностные копии в файл с полной копией

SQL Server позволяет хранить несколько наборов резервных копий в одном физическом файле. Для этого при создании полной копии используется `WITH INIT` (очистка файла), а при добавлении последующих копий — `WITH NOINIT` (дописывание в конец файла). При восстановлении нужный набор выбирается параметром `WITH FILE = n`, где `n` — порядковый номер набора в файле.

```sql
BACKUP DATABASE MyDB
TO DISK = 'C:\Backups\MyDB_Combined.bak'
WITH INIT, NAME = 'Full';

-- ... something happens with data in DB ...

BACKUP DATABASE MyDB
TO DISK = 'C:\Backups\MyDB_Combined.bak'
WITH DIFFERENTIAL, NOINIT, NAME = 'Diff 1';

-- ... something happens with data in DB ...

BACKUP DATABASE MyDB
TO DISK = 'C:\Backups\MyDB_Combined.bak'
WITH DIFFERENTIAL, NOINIT, NAME = 'Diff 2';

-- Check file content
RESTORE HEADERONLY
FROM DISK = 'C:\Backups\MyDB_Combined.bak';

RESTORE DATABASE MyDB
FROM DISK = 'C:\Backups\MyDB_Combined.bak'
WITH FILE = 1, REPLACE, NORECOVERY;

RESTORE DATABASE MyDB
FROM DISK = 'C:\Backups\MyDB_Combined.bak'
WITH FILE = 3, RECOVERY;
```

### 11. Индивидуальная стратегия резервного копирования

Ниже приведены основные типы копий, которые могут использоваться:

| Тип копии | Команда | Назначение |
|---|---|---|
| Полная | `BACKUP DATABASE ... WITH INIT` | Базовая копия всех данных |
| Разностная | `BACKUP DATABASE ... WITH DIFFERENTIAL` | Изменения с момента последней полной копии |
| Журнал транзакций | `BACKUP LOG` | Все транзакции с момента последней копии лога |
| Копия для копирования | `BACKUP DATABASE ... WITH COPY_ONLY` | Не нарушает цепочку разностных копий |
| Файловая группа | `BACKUP DATABASE ... FILEGROUP = 'FG'` | Копия конкретной файловой группы |
| Хвост журнала | `BACKUP LOG ... WITH NO_TRUNCATE` | Копия журнала при повреждении БД |

> **Примечание.** Копия для копирования (`COPY_ONLY`) не влияет на цепочку разностных копий и не сбрасывает дифференциальную базу. Используйте её, когда необходимо создать «*внеплановую*» копию, не нарушая расписание основного резервного копирования.

```sql
BACKUP DATABASE MyDB
TO DISK = 'C:\Backups\MyDB_CopyOnly.bak'
WITH COPY_ONLY, INIT;

BACKUP LOG MyDB
TO DISK = 'C:\Backups\MyDB_Log.trn'
WITH INIT;

BACKUP DATABASE MyDB
FILEGROUP = 'FG_Archive'
TO DISK = 'C:\Backups\MyDB_FG_Archive.bak'
WITH INIT;
```

### 12. Имитация сбоев и восстановление

Для каждого сценария из вашего варианта выполните следующие шаги:
1. Зафиксируйте текущее состояние БД (создайте резервную копию, если это требуется сценарием).
2. Воспроизведите сбой (удаление данных, повреждение файла и т. д.).
3. Выполните восстановление, используя соответствующие резервные копии.
4. Убедитесь, что данные восстановлены корректно.

**Точечное восстановление (Point-in-Time Recovery).** Позволяет восстановить БД на конкретный момент времени. Применяется, когда известно время ошибочной операции (например, случайный `DELETE`).

```sql
-- Tail-log copy before restore
BACKUP LOG MyDB
TO DISK = 'C:\Backups\MyDB_TailLog.trn'
WITH NO_TRUNCATE, INIT;

RESTORE DATABASE MyDB
FROM DISK = 'C:\Backups\MyDB_Full.bak'
WITH REPLACE, NORECOVERY;

-- Restore log at moment BEFORE crash
RESTORE LOG MyDB
FROM DISK = 'C:\Backups\MyDB_Log.trn'
WITH NORECOVERY;

RESTORE LOG MyDB
FROM DISK = 'C:\Backups\MyDB_TailLog.trn'
WITH STOPAT = '2026-10-01 14:30:00', RECOVERY;
```

**Восстановление файловой группы.** Применяется при повреждении отдельного файла или файловой группы. Остальные файловые группы остаются доступными.

```sql
-- Restore damaged FG
RESTORE DATABASE MyDB
FILEGROUP = 'FG_Archive'
FROM DISK = 'C:\Backups\MyDB_FG_Archive.bak'
WITH NORECOVERY;

RESTORE LOG MyDB
FROM DISK = 'C:\Backups\MyDB_Log.trn'
WITH RECOVERY;
```

### ВАЖНО

> - Все операции резервного копирования и восстановления выполняйте в **полной модели восстановления**. В простой модели копии журнала транзакций недоступны.
> - После восстановления базы данных из резервной копии цепочка журнала транзакций прерывается. Необходимо создать новую полную копию для продолжения регулярного резервного копирования.
> - Копия хвоста журнала (`Tail-Log`) создаётся **после** возникновения сбоя и **до** начала восстановления. Если файл журнала транзакций повреждён, используйте `WITH NO_TRUNCATE` или `WITH CONTINUE_AFTER_ERROR`.
> - При восстановлении файловой группы база данных должна оставаться в режиме `NORECOVERY` до тех пор, пока все файловые группы не будут согласованы с журналом транзакций.
> - Лабораторная версия SQL Server не поддерживает сжатие и шифрование резервных копий. Не используйте параметры `COMPRESSION` и `ENCRYPTION` в командах `BACKUP`.
> - Храните резервные копии на диске, отличном от диска с файлами базы данных, чтобы имитация сбоя (удаление файлов) не затронула копии.
